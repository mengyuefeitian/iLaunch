# Design: Icon Size Boost + Auto-Update (Sparkle)

## 1. Icon size ×1.1

### Objective
Increase the rendered app-icon size at all three grid density levels (small/medium/large) by 1.1×, without changing grid cell/tile dimensions.

### Change
`Sources/iLaunch/Models/UserPreferences.swift`, `IconSizeLevel.multiplier`:

| Level  | Current | New (×1.1) |
|--------|---------|------------|
| small  | 0.65    | 0.715      |
| medium | 0.80    | 0.88       |
| large  | 1.0     | 1.1        |

This multiplier only scales `drawnIconSize` in `AppIconView` (icon artwork), not `tileWidth`/`cellSize` (grid layout), per the existing doc comment on `IconSizeLevel`. `FolderPopupView`'s folder-tile sizing (`folderTileWidth`, `folderIconSize`, `folderTileHeight`) also derives from this multiplier and scales proportionally — expected and consistent with existing behavior.

### Testing
Existing tests (if any) covering `IconSizeLevel.multiplier` get updated to the new expected values. No new test scaffolding needed — this is a constant change, not new logic.

### Boundaries
- Always: keep values as flat ×1.1 of the current constants (per user approval).
- Never: touch grid cell dimensions (`GridMetrics.tileWidth`, `cellSize`) — out of scope.

## 2. Auto-update via Sparkle

### Objective
Give the app daily background update checks and a one-click "download, verify, install, relaunch" update flow, matching what popular open-source macOS apps (Rectangle, Stats, etc.) ship via the Sparkle framework. This was previously listed as a "planned" v2.0 item in `README_en.md`.

### Constraints
- App is ad-hoc signed (`codesign --force --deep --sign -`), no Apple Developer ID or notarization.
- Built via plain `swift build` + a hand-rolled bundling script (`script/build_and_run.sh`), not an Xcode project — so nothing auto-embeds frameworks or sets up rpaths the way Xcode would.
- Distributed via GitHub Releases at `github.com/mengyuefeitian/iLaunch`.

### Tech Stack Addition
- Dependency: `sparkle-project/Sparkle` via SPM, pinned to the latest stable release tag at implementation time.
- Sparkle's `SPUStandardUpdaterController` (AppKit-based standard UI) — no custom update UI.

### Components

**`Sources/iLaunch/Services/UpdateService.swift`** (new)
- Wraps `SPUStandardUpdaterController`.
- `checkForUpdates()` — manual trigger for the menu item (delegates to `updaterController.checkForUpdates(_:)`).
- On init: sets `updater.automaticallyChecksForUpdates = true`, `updater.updateCheckInterval = 86400` (daily).
- Owns no UI of its own — Sparkle's standard controller presents its own alerts/progress windows.

**`AppDelegate`**
- Instantiates `UpdateService` once at launch (same lifecycle tier as `MenuBarController`, `GlobalHotKeyManager`).

**`MenuBarController`**
- New `NSMenuItem` "Check for Updates…" (localized key `menubar.checkForUpdates`), placed after the existing `settingsItem`/`logsItem`, before the separator/quit item.
- Action calls `UpdateService.checkForUpdates()`.

**`Localizer`**
- Add `menubar.checkForUpdates` string for every language currently supported (`system` fallback uses English/Chinese as the existing pattern does — follow whatever `menubar.settings` does per-language).

### Build/Packaging Changes

**`Package.swift`**
- Add `.package(url: "https://github.com/sparkle-project/Sparkle", from: "<pinned-version>")` and `"Sparkle"` as a dependency of the `iLaunch` executable target.
- Add linker setting on the executable target: `.unsafeFlags(["-Xlinker", "-rpath", "-Xlinker", "@executable_path/../Frameworks"])` so the binary resolves `Sparkle.framework` relative to `Contents/MacOS/../Frameworks` at runtime.

**`script/build_and_run.sh`**
- After `swift build` and before `codesign`, add a step that locates the built `Sparkle.framework` (from SPM's `.build` artifacts / checkout resources) and copies it into `$APP_CONTENTS/Frameworks/Sparkle.framework`, creating the `Frameworks` directory if needed.
- No change to the existing `codesign --deep` call — it already recursively signs embedded frameworks.

**`Info.plist` (generated in `build_and_run.sh`)**
- `SUFeedURL` → `https://mengyuefeitian.github.io/iLaunch/appcast.xml` (GitHub Pages, served from `docs/appcast.xml` on `master`, since `docs/` already exists in this repo).
- `SUPublicEDKey` → the EdDSA public key generated by Sparkle's `generate_keys` tool (committed to the repo/script; the private key is never committed).
- `SUEnableAutomaticChecks` → `true`, `SUScheduledCheckInterval` → `86400`.

### Release/Signing Process (manual, not CI)
1. Tag and build the release `.dmg` as today (`script/package_dmg.sh`).
2. Sign the `.dmg` with Sparkle's `sign_update` CLI tool using the private EdDSA key (kept locally, not in git).
3. Regenerate `appcast.xml` (Sparkle's `generate_appcast` tool, or hand-edit for a single-entry feed) with the new version, signature, and download URL (GitHub Release asset URL).
4. Publish `appcast.xml` to `docs/appcast.xml` on `master` (GitHub Pages picks it up automatically once Pages is enabled for the repo, pointed at `/docs`).
5. Push the tagged `.dmg` as a GitHub Release asset as already done.

This stays a manual per-release step for now; automating it via GitHub Actions is explicitly out of scope for this design and can be a follow-up.

### Error Handling
- Network failures during a check: Sparkle's standard UI silently no-ops for scheduled background checks (no interruption) and shows a native error alert only for user-initiated manual checks — this is Sparkle's default behavior, not custom code.
- Signature verification failure: Sparkle refuses to install and shows its standard error alert — default behavior, not custom code.

### Testing
- `UpdateServiceTests` (new, in `Tests/iLaunchTests/`): verifies `UpdateService` configures `automaticallyChecksForUpdates == true` and `updateCheckInterval == 86400` after init. This is the only logic that's actually ours to test — the download/verify/install/relaunch pipeline is Sparkle's own, already covered by Sparkle's test suite, and isn't practical to re-test here (it requires a live feed and real binaries).
- Manual verification: after the first tagged release with a working appcast, install an older build and confirm the full check → prompt → one-click install → relaunch flow works end-to-end on a real machine.

### Boundaries
- Always: keep the private signing key out of git; ad-hoc `codesign --deep` continues to cover the embedded framework.
- Ask first: enabling GitHub Pages for the repo (a repo-settings change, not code) — flag it to the user rather than assuming it's already on.
- Never: automate the release-signing pipeline into CI as part of this change — that's a separate, later decision.

## Success Criteria
- Icon size: all three `IconSizeLevel` multipliers reflect the new ×1.1 values; existing grid layout untouched.
- Auto-update: app checks for updates once daily in the background without user action; a "Check for Updates…" menu item triggers an on-demand check; when an update is found, one click on Sparkle's standard "Install Update" button downloads, verifies, installs, and relaunches the app with no further user interaction.

## Open Questions
- None blocking. GitHub Pages must be enabled on the repo for the appcast URL to resolve — will confirm with the user before/at release time.
